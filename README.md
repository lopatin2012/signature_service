# Signature Service

Микросервис для создания электронных подписей (CAdES-BES) через FastAPI.
Кроссплатформенный: работает на Windows (win32com/CAdESCOM) и Linux (pycades/КриптоПро CSP).

## Возможности

- Прикреплённая (`attached`) и откреплённая (`detached`) подписи CAdES-BES.
- Единый интерфейс `BaseSigner` для обеих платформ; signer создаётся один раз при старте (singleton).
- Fail-fast при запуске: если криптопровайдер недоступен, сервис не стартует.
- Ретраи с экспоненциальной паузой только для транзиентных ошибок.
- Жёсткий таймаут операции подписи (по умолчанию 60 с).
- Ошибки возвращаются с текстом ошибки и подсказкой на русском, что делать.
- Опциональная аутентификация по API-ключу (`X-API-Key`).

## Запуск

```bash
python main.py
```

По умолчанию сервер слушает `0.0.0.0:8101`. Хост, порт и остальные настройки
берутся из переменных окружения. При старте приложение автоматически загружает
файл `.env` из корня проекта (python-dotenv); уже заданные переменные окружения
имеют приоритет и не перезаписываются:

```bash
export SERVICE_HOST="0.0.0.0"
export SERVICE_PORT=8101
```

Интерактивная документация API: <http://localhost:8101/docs>.

## Конфигурация

| Переменная | По умолчанию | Описание |
|------------|--------------|----------|
| `SERVICE_HOST` | `0.0.0.0` | Адрес прослушивания |
| `SERVICE_PORT` | `8101` | Порт |
| `SIGNING_TIMEOUT_SECONDS` | `60` | Жёсткий таймаут подписи (сек.) |
| `MAX_SIGNING_RETRIES` | `3` | Максимум попыток при транзиентных ошибках |
| `BASE_RETRY_DELAY_SEC` | `1.0` | Базовая пауза экспоненциального бэк-оффа (сек.) |
| `API_KEY_HEADER_NAME` | `X-API-Key` | Имя заголовка для API-ключа |
| `API_KEYS` | — | Список ключей через запятую (`foo,bar,baz`) |
| `SERVICE_API_KEY` | — | Одиночный API-ключ (если `API_KEYS` не задан) |
| `CERT_PATH` | `/certs/cert.pfx` | Путь к PFX (Linux, необязательно) |
| `CERT_PASSWORD` | — | Пароль PFX (Linux, необязательно) |

Значения можно положить в `.env` в корне проекта — они загружаются при старте.
Переменные, уже заданные в окружении (например, через `export`), имеют приоритет
над `.env`.

## API

| Метод | Путь | Описание |
|-------|------|----------|
| `GET` | `/` | Информация о сервисе и список эндпоинтов |
| `GET` | `/api/health` | Статус сервиса и количество сертификатов (liveness-проба) |
| `GET` | `/api/certificates/` | Список валидных сертификатов из хранилища |
| `POST` | `/api/sign/attached/` | Прикреплённая подпись (содержимое внутри подписи) |
| `POST` | `/api/sign/unpinned/` | Откреплённая подпись (без содержимого документа) |

### Запрос на подпись

```json
POST /api/sign/attached/
{
  "data": "данные для подписания",
  "serial_number": "AB12CD34EF56"
}
```

- `data` — строка до 10 МБ; перед подписью кодируется в UTF-8.
- `serial_number` — серийный номер сертификата, 8–64 символа.

### Успешный ответ

```json
{
  "status": "success",
  "signed_data": "MII...(base64 подпись)",
  "signing_time_ms": 12
}
```

### Список сертификатов

```json
GET /api/certificates/
{
  "certificates": [
    {
      "serial_number": "AB12CD34EF56",
      "subject": "Иванов Иван",
      "issuer": "Удостоверяющий центр ...",
      "valid_from": "01-01-2025",
      "valid_to": "01-01-2030",
      "thumbprint": null
    }
  ],
  "count": 1
}
```

Возвращаются только сертификаты, у которых осталось не менее 1 дня действия
(на Linux даты приходят из КриптоПро в формате `DD.MM.YYYY HH:MM:SS`).

### Health check

```json
GET /api/health
{
  "status": "healthy",
  "signer_available": true,
  "certificates_count": 1
}
```

Возвращает `200`, если signer доступен, и `503` — если нет. Подходит для
`livenessProbe` в Kubernetes/Docker.

### Ошибки

Ответ об ошибке содержит подсказку на русском и текст ошибки
(`detail = "подсказка... Ошибка: <текст>"`).

| Код | Когда | Подсказка |
|-----|-------|-----------|
| `404` | Сертификат с таким серийным номером не найден/недействителен | Проверить серийный номер, наличие сертификата в хранилище и срок действия |
| `422` | Некорректное тело запроса (нет `serial_number`, слишком короткий и т.п.) | Проверить формат запроса |
| `401` | Неверный или отсутствующий API-ключ (если аутентификация включена) | Передать корректный ключ в заголовке `X-API-Key` |
| `500` | Сбой криптопровайдера, таймаут, внутренняя ошибка | Проверить журнал сервиса; при таймауте увеличить `SIGNING_TIMEOUT_SECONDS` |
| `503` | Signer не инициализирован | Проверить журнал запуска сервиса |

### Аутентификация (опционально)

Если задан `SERVICE_API_KEY` или `API_KEYS=foo,bar,baz`, все эндпоинты требуют
заголовок с валидным ключом:

```bash
curl -H "X-API-Key: foo" http://localhost:8101/api/health
```

Если ключи не сконфигурированы, аутентификация не выполняется.

### Примеры с curl

```bash
# Прикреплённая подпись
curl -X POST http://localhost:8101/api/sign/attached/ \
  -H "Content-Type: application/json" \
  -d '{"data": "текст документа", "serial_number": "AB12CD34EF56"}'

# Откреплённая подпись
curl -X POST http://localhost:8101/api/sign/unpinned/ \
  -H "Content-Type: application/json" \
  -d '{"data": "текст документа", "serial_number": "AB12CD34EF56"}'

# Список сертификатов
curl http://localhost:8101/api/certificates/
```

> **Postman:** отправляйте тело как **JSON** — вкладка `Body` → `raw` → тип `JSON`,
> а не `form-data`. Иначе сервис вернёт `422` с подсказкой про формат тела.

## Надёжность

- **Fail-fast при старте.** Signer — singleton, создаётся в lifespan приложения.
  Если криптопровайдер недоступен или хранилище не читается, сервис завершает
  работу (`SystemExit`) вместо того, чтобы отдавать ошибки на каждый запрос.
- **Ретраи.** Транзиентные ошибки (категории `NETWORK_OR_IO`, `TEMPORARY_RESOURCE`,
  а также `OSError`) повторяются до `MAX_SIGNING_RETRIES` раз с экспоненциальной
  паузой (база `BASE_RETRY_DELAY_SEC`, максимум = таймаут × 2). Ошибки
  сертификата/данных не ретраятся.
- **Таймаут.** Блокирующие вызовы COM/pycades выполняются в отдельном потоке
  (`asyncio.to_thread`), поэтому `asyncio.wait_for` действительно прерывает
  зависшую операцию по истечении `SIGNING_TIMEOUT_SECONDS`.
- **Освобождение COM-объектов.** На Windows все COM-объекты освобождаются до
  `CoUninitialize()` (иначе pythoncom печатает `Win32 exception occurred releasing
  IUnknown`).

## Платформы

### Windows

- Криптопровайдер: CAdESCOM через `win32com` (пакет `pywin32`), сборка не нужна.
- Сертификаты: хранилище текущего пользователя `Cert:\CurrentUser\My`,
  поиск по серийному номеру.
- К подписи добавляется атрибут времени подписи (timestamp).

### Linux

- Криптопровайдер: КриптоПро CSP, библиотека `pycades`, машинное хранилище `mMy`.
- **Важно:** официальный wheel `pycades` сломан — он не видит системные
  библиотеки CSP. Ставьте из исходников:

  ```bash
  git clone https://github.com/CryptoPro/pycades.git
  cd pycades && pip install .
  ```

- Импортируйте PFX в машинное хранилище до первого запроса:

  ```bash
  cryptonets --store mMy -pfx import your-cert.pfx password
  ```

- Атрибуты времени подписи на Linux не добавляются (ограничение pycades).

## Docker

```bash
docker compose up -d --build
```

Образ собирается из исходников (чтобы pycades линковался с системным CSP),
сертификат монтируется из `certs/cert.pfx`, пароль передаётся через
`CERT_PASSWORD` (см. `.env`). При подъёме контейнера автоматически запускается
`python main.py --selftest`.

## Тестирование

Зависимости для тестов (`pytest`, `httpx`) включены в `requirements.txt`.

```bash
# Быстрые API-тесты с фейковым signer'ом (криптопровайдер не нужен)
python -m pytest -q -m 'not cert' tests/

# Интеграционные тесты с реальным криптопровайдером (требуют сертификат в хранилище)
python -m pytest tests/test_certificate.py -m cert -v

# Авто-тесты перед стартом: сервис не запустится, если тесты не пройдены
python main.py --selftest
```

Команды доступны также через `make` (`make test`, `make test-cert`, `make selftest`,
`make lint`, `make typecheck`).

## Как это работает

При старте `signers/__init__.py` определяет ОС и создаёт экземпляр
`WindowsSigner` или `LinuxSigner`. Все запросы на подпись обрабатываются через
единый интерфейс `BaseSigner`, который возвращает кортеж
`(base64-подпись, SigningResult)`; категории ошибок (`SigningErrorCategory`)
определяют, ретраить ли операцию и какой HTTP-статус вернуть.

На **Windows** каждая операция выполняется в COM-контексте
(`CoInitialize`/`CoUninitialize`); сертификат ищется в хранилище по серийному
номеру, COM-объекты освобождаются до разъинициализации.

На **Linux** используется КриптоПро CSP: сертификат с приватным ключом должен
быть импортирован в машинное хранилище `mMy`, подпись создаётся через pycades
в рамках одного открытого хранилища.
